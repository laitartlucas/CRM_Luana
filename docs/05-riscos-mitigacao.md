# Riscos Técnicos e Mitigação

| # | Risco | Impacto | Mitigação |
|---|---|---|---|
| 1 | Reprovação/demora na aprovação de templates de mensagem da Meta (lembrete, confirmação) | Alto — sem template aprovado, não é possível iniciar conversa fora da janela de 24h de atendimento | Iniciar Fase 0.2 o quanto antes; usar `MockWhatsappProvider` para desenvolvimento/demo em paralelo; ter templates de fallback simples e genéricos prontos para reenvio caso um seja rejeitado. |
| 2 | Loop de duplicação entre CRM e Google Calendar (evento sincronizado gera novo evento, que gera novo evento...) | Alto — polui a agenda real do profissional | `Appointment.source` + `googleEventId` como chave de dedupe (ver `02-modelo-de-dados.md` §2); toda escrita originada por webhook do Google é marcada antes de qualquer callback de volta ser processado; testes automatizados cobrindo especificamente ida-e-volta. |
| 3 | Token OAuth do Google expira ou é revogado sem o profissional perceber | Médio — sync para de funcionar silenciosamente | Healthcheck `/health/calendar` visível no dashboard; job de renovação proativa de refresh token; notificação (e-mail/WhatsApp interno) quando a sync falhar por N tentativas seguidas. |
| 4 | Rate limit da Meta Cloud API ou do Google Calendar API | Médio | Filas com BullMQ já absorvem picos; backoff exponencial + respeito a `Retry-After`; batching de chamadas ao Google quando possível. |
| 5 | Webhook (Meta ou Google) indisponível momentaneamente derruba o restante do sistema | Alto se não isolado | Arquitetura já isola isso por design (provider pattern + fila + circuit breaker, ver `01-arquitetura.md` §7); testes de chaos simples (matar a integração e confirmar que login/agenda/clientes continuam operando) fazem parte do checklist de release. |
| 6 | Condição de corrida: dois agendamentos simultâneos para o mesmo horário (um pela web, outro pelo WhatsApp) | Médio | `AppointmentsService` como única porta de escrita + constraint `EXCLUDE` no Postgres como árbitro final; erro de conflito tratado como resposta normal do fluxo (bot oferece outro horário), não como exceção não tratada. |
| 7 | Vazamento de dados sensíveis (medidas, fotos, restrições, telefone) — LGPD | Alto (jurídico + reputacional) | Consentimento explícito armazenado com timestamp/origem; tokens e PII sensível criptografados em repouso; endpoint de exclusão/anonimização; log de auditoria cobrindo leitura/exportação, não só escrita; princípio de menor privilégio nos papéis (atendente não vê tudo que admin vê, conforme regra de negócio a definir). |
| 8 | Custo/latência de um provedor de IA (Fase 2, assistente de WhatsApp) tornando a conversa lenta ou cara | Médio | Motor de estados determinístico continua existindo por baixo (ver `03-fluxos-whatsapp.md`); LLM só interpreta intenção, com fallback automático para o menu numérico se a chamada de IA falhar ou demorar mais que um timeout curto. |
| 9 | Fuso horário incorreto gerando agendamento na hora errada | Alto (impacto direto no cliente final) | Armazenamento único em UTC; conversão só na borda (frontend/mensagens de WhatsApp); testes automatizados cobrindo horário de verão/mudanças de fuso. |
| 10 | Crescimento de volume além do dimensionado (mais profissionais, mais unidades) exigindo retrabalho | Baixo no MVP, médio a longo prazo | Modelo de dados já isola por `professionalId`; caminho de migração para multi-tenant documentado na Fase 3 (`04-plano-implementacao.md`). |
| 11 | Dependência de um único desenvolvedor/consultoria para manter as integrações (Meta e Google mudam APIs com frequência) | Médio | Provider pattern mantém o código de integração concentrado em 2 arquivos por serviço, isolado do resto do domínio — troca de versão de API não deveria tocar em `appointments`/`clients`. Documentação (este pacote de docs) e testes automatizados reduzem a dependência de conhecimento tácito. |
| 12 | Ambiente de desenvolvimento sem Docker/Postgres/Redis instalados localmente (situação atual da máquina usada nesta implementação) | Baixo | Código foi escrito e validado via compilação TypeScript/Prisma sem exigir os serviços rodando; `docker-compose` documentado é o caminho recomendado assim que Docker Desktop estiver disponível; README traz alternativa com Postgres/Redis locais. |
